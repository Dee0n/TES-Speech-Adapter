# Нарратор-агент: аудит и схема (2026-10-03)

Этап B ROADMAP: «возврат результата в LLM, многошаговый цикл» + «реестр действий данными».
Документ — проект. Ничего из нового ещё не применено.

## 1. Как сейчас (аудит) `[код]`

```
игрок ─► narrator_inputtext ─► main.php ─► call_llm()  (ОДИН вызов)
                                             │
                     JSON {message, action, target}   ← одна строка-действие за ход
                                             │
           action = GodCommand, target = строка-DSL «{npc:Назим}.relation 100 friend; coc …»
                                             │
            tes_god_guard (1776 строк regex) ─► herikaQueueGodCommands ─► outbox
                                             │                               │
                                  .relation/.character → БД             плагин: консоль
                                                                             │
                                          tes_god_console (logMessage) ─► таблица, terminate
                                                                             │
                                       следующий ход: журнал в промпте (tes_god_journal)
```

Что из этого следует:
1. **Протокол — свободный текст.** Все параметры Нарратора лежат в одной строке `target`, и страж
   разбирает её регулярками. Отсюда склейки команд без `;`, «Title:» в названии документа,
   выдуманные FormID. Чинилось точечно (0f7e879, ea58f83). Источник ошибок остаётся.
2. **Цикла нет.** Нарратор делает ход вслепую, результат видит только в следующем ходе, и только
   если игрок снова к нему обратится.
3. **В CHIM уже есть механизм повтора — `funcret`** (`processor/funcret.php`). Игра возвращает
   результат действия, сервер делает второй вызов LLM с `role: tool`. Метаданные `followup`
   в `core_action` (prompt, use_functions_again). Живьём работает: InspectSurroundings, CheckInventory,
   Inspect 2026-10-03. Ограничения: глубина цепочки жёстко `return 1`
   (`lib/core/action_catalog.php:1313`), и срабатывает он только для действий, которые исполняет
   игра (`plugin_command`). Консольные команды Нарратора идут через outbox и сюда не попадают.
4. **`dispatch: server_query` объявлен, но обработчика нет** (`action_catalog.php:1508` —
   единственное упоминание). То есть «серверный запрос с ответом модели» в CHIM задуман, но не сделан.
5. `parameters_json` действия может описывать несколько полей (SpawnItem: item/amount/target), так что
   типизированные инструменты возможны средствами CHIM, без нового диалекта.
6. Две ошибки из обсуждения уже закрыты: склеенные команды режутся (0f7e879), `.relation` ставит
   `relationships_locked`, `.character` — `lock_profile` (TES-GOD-LOCK, живьём 01:55 на Назиме).

## 2. Целевая схема

```
игрок ─► [0] ВОСПРИЯТИЕ (ext context_pre, 0 вызовов LLM)
             имена из реплики → NPC (RefID, жив, где, отношение к игроку, lock), места, предметы,
             золото игрока, дома и их владельцы
        ─► LLM ─► [1] ТИПИЗИРОВАННЫЙ ИНСТРУМЕНТ (строка core_action, JSON-поля)
                       │
                  [2] ВАЛИДАТОР (ext): неизвестный инструмент / поле / ID → ОТКАЗ,
                       ничего не пишется. Причина уходит модели (в цикле) и игроку (уведомление).
                       │
     ┌─────────────────┼──────────────────────────┐
  server_write      server_query               game_action
  (отношение,       (найти NPC/место/          (телепорт, предметы,
   память)           предмет, состояние)        setstage, moveto)
     │                 │                           │
  записать и         результат → 2-й вызов       outbox → консоль → ПРОВЕРКА ПО СОСТОЯНИЮ
  СРАЗУ перечитать   LLM в том же запросе        (getitemcount, getstagedone, activity_status),
  → «было → стало»   (лимит 3 шага)              не по тексту консоли (ReadMessage врёт при
                                                  параллельных командах) → фоновый
                                                  follow-up Нарратора в responselog
```

### Слои данных NPC — кто что может менять

| Слой | Инструмент | Кто | Защита |
|---|---|---|---|
| отношение | `SetRelationship {npc, value, type, reason}` | Нарратор | ставит `relationships_locked`, перечитывает |
| память | `Remember {npc, text}` | Нарратор | гигиена противоречий (уже есть) |
| состояние/место | `MoveNPC`, `TeleportPlayer` | Нарратор | проверка по `activity_status` |
| характер | `SetCharacter` / `.hypnosis` | **вопрос владельцу** (см. §5) | `lock_profile` |
| действие в мире | `GiveItem`, `SellProperty`, … | Нарратор, NPC по роли | валидатор + проверка |
| текст | `message` | все | — |

Персонаж-поле может меняться ТОЛЬКО через свой инструмент. Строка, похожая на команду, в поле профиля
не пишется никогда: сомнение → отказ.

`GodCommand` (сырая консоль) остаётся запасным выходом под тем же стражем, но рецепты
`.relation/.character/.document` из подсказки уходят в инструменты.

## 3. Первый вертикальный срез — Провентус продаёт Breezehome

Ванильный механизм `[код]` (`HousePurchaseScript.psc`, `QF_HousePurchase_000A7B33.psc`,
`TIF_PlayerHouseBuySold_000C6E28.psc`): реплика управляющего вызывает `setstage HousePurchase 10`.
Фрагмент стадии делает всё сам: `RemoveItem(Gold, HPWhiterun)`, ключ, книга обустройства,
`SetFactionOwner(PlayerFaction)` на интерьер, статистика «Houses Owned», задача 10,
`Favor253` (тан) 10→15, усыновление (BYOH). То же для Солитьюда/Рифтена/Маркарта/Виндхельма
(стадии 20–50, `[гипотеза]` по нумерации задач — сверить по ESM).

Инструмент `SellProperty {house}` (NPC с ролью управляющего + Нарратор):
1. Восприятие: цена = глобал `HPWhiterun` (читать из ESM индексом; Requiem может менять —
   проверить его override), золото игрока, стадия 10 уже пройдена?
2. Валидатор: дом известен, не куплен, золота ≥ цены. Иначе отказ с причиной (модель
   торгуется/отказывает в роли).
3. Игра: `setstage HousePurchase 10`.
4. Проверка: `getstagedone HousePurchase 10` = 1 и ключ в инвентаре; follow-up Провентуса
   одной фразой («ключ ваш»).
Без вымышленных бумаг: договор (`WriteDocument`) — дополнение, а не замена.

Риски `[гипотеза]`: `RemoveItem` не проверяет сумму (надо проверять самим, иначе дом за полцены);
ванильный диалог продажи после этого исчезнет сам (условие `WhiterunHouseVar`).

## 4. Цена и скорость

Шаг цикла = ещё один вызов LLM: ~3–6 с и ~$0.0003 (MiMo V2.6 Flash) / ~$0.0006 (Gemini 3.8 Flash).
Лимит 3 шага → худший ход Нарратора +15 с. Восприятие (слой 0) снимает большую часть шагов
«найди → прочитай» бесплатно, поэтому оно идёт первым.

Честные ограничения:
- Первая реплика (`message`) уже произнесена, пока инструмент работает → follow-up-подсказка
  «одна короткая фраза, не повторяйся» (как у ReadQuestJournal).
- Игровые действия асинхронны: подтверждение приходит через 1–3 с отчётом консоли, отдельным запросом.
- Живой ответ MiMo в `funcret`-цепочке не проверен (последние успешные — 02:21–02:24).

## 5. Открытый вопрос владельцу

Предложение из обсуждения: «Нарратор вообще не меняет personality». Раньше владелец явно хотел,
чтобы бог менял характер (`.character`, `.hypnosis`). Что главнее?
(а) запретить; (б) только через `SetCharacter` с `lock_profile` и записью «было → стало».

## 6. Порядок работ и что требует «да»

| # | Шаг | Где | «да»? |
|---|---|---|---|
| 1 | Восприятие (слой 0) | ext `tes_agent` context_pre | нет |
| 2 | Валидатор и обработчики инструментов | ext `tes_agent` functions.php | нет |
| 3 | Новые строки `core_action` (инструменты, SellProperty) | SQL, только INSERT, откат DELETE | **да** |
| 4 | Цикл `server_query`: после `call_llm` выполнить запрос и вызвать LLM ещё раз (≤3) | ядро `main.php` | **да** |
| 5 | Глубина follow-up 1 → 3 | ядро `action_catalog.php:1313` | **да** |
| 6 | Фоновый follow-up после проверки игрового действия | ext + воркер (как SNQE) | нет |
| 7 | Подсказка Нарратора: рецепты → инструменты | SQL `core_narrator` | **да** |
